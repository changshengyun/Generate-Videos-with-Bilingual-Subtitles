# V3-AI-001 检索增强 Spike

## SP-A：歌词源可用性

- 假设：只读搜索端点能按歌名/歌手返回包含完整英文歌词的候选。
- 实验：使用非用户数据的已知歌曲元数据调用一次搜索，只记录 HTTP 状态、候选数、歌词行数和哈希，不记录歌词正文。
- 通过：HTTPS 成功，至少一个候选包含非空完整歌词。
- 失败解释：只否决当前歌词源，不否决 SearchTool 架构。
- 清理：无持久产物。

## SP-B：错误候选可拒绝

- 假设：现有对齐器经批次评分扩展后能接受正确歌词并拒绝错误歌曲。
- 实验：正例 Whisper 片段、轻微 ASR 错误和无关歌词三类 JVM 夹具。
- 通过：正例和轻微错误通过，无关歌词拒绝；阈值以夹具结果冻结。
- 失败解释：需要改进评分，不允许绕过验证。

## SP-C：整首上下文合同

- 假设：两步 Provider 能把已验证完整歌词放入第二次请求，并严格保持 cue 身份。
- 实验：假 SearchTool + 假连接的 focused JVM 测试。
- 通过：请求包含完整歌词；响应 cue 集、顺序和时间保持；检索失败不声明确认。
- 清理：测试内存数据，无外部产物。
